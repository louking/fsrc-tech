# tmtility

Manages results received from a Time Machine manual race timer for input to scoring software like [RaceDay Scoring](https://info.runsignup.com/products/raceday/raceday-scoring/). Its main purpose is to be the backup when chip reads are missed, so operator aids can use chip reads when present but must also work without them.

- Repo: https://github.com/louking/tm-csv-connector
- Docs: https://tm-csv-connector.readthedocs.io/en/latest/
- Repo's own `CLAUDE.md` (authoritative, deeper detail than this page): https://github.com/louking/tm-csv-connector/blob/master/CLAUDE.md
- Runs on a laptop, so there's no publicly accessible site
- Receives results from the [Time Machine](https://timemachine.org/) over Bluetooth, bib numbers scanned from participant bibs, and optionally chip reads from a Trident RFID reader
- Creates a CSV file which can be read by race scoring software (designed for and tested with RaceDay Scoring)
- Also runs in "simulator mode" so a prospective scoring operator can practice
- For chip-timing (Trident) theory, configuration, and race-day operation this app fits into, see [race-services/timing.md](../race-services/timing.md)

## Tech stack

- Backend: Flask, SQLAlchemy, Flask-Migrate (Alembic)
- Frontend: Jinja2, flask-assets bundles, WebSocket-driven live results view (`results.js`)
- Packaging: PyInstaller-built Windows client executables, distributed as zips and installed via NSSM as Windows services
- Shared libraries: [loutilities](../framework/loutilities.md) (`DbCrudApi` for table views)

## Architecture notes

- **Two operating modes**, toggled by `SIMULATION_MODE`: normal mode auto-logs in a default user, shows public views only, and talks to real hardware; simulation mode exposes full multi-user login and `/admin/*` routes, replaying recorded events for operator training.
- **Three external client processes** run as Windows services (not in the Docker container, since they need direct access to USB/Bluetooth hardware): `tm-reader-client` (Time Machine Bluetooth), `barcode-scanner-client` (bib scanner), `trident-reader-client` (Trident RFID telnet connection). Each connects to the Flask backend over WebSocket and also POSTs results directly.
- **Data model duality**: `Result` and `ScannedBib` each carry two nullable foreign keys — `race_id` (normal mode) and `simulationrun_id` (simulation mode) — exactly one is ever non-null, and queries must filter on the right one.
- **File locking**: a `threading.Lock` (`fileformat.filelock`) serializes any operation touching the CSV output file or related multi-table DB writes (place recalculation, scanned-bib queue assignment).
- **Race start time**: `Race.start_time` is the time-of-day offset added to Time Machine elapsed times when writing the CSV, and is shown on the results view for on-site verification. It can be set manually or auto-populated from the first live Trident `GUNTIME` marker for a race — but only once; later markers are ignored.
- **Tests**: two pytest suites ([tm-csv-connector#166](https://github.com/louking/tm-csv-connector/issues/166), [#167](https://github.com/louking/tm-csv-connector/issues/167)). The app tests run in the dev app container against a separate `tm-csv-connector-test` database rebuilt on each run, with the output CSV in a temporary directory, so dev data and the real CSV aren't touched. Simulation mode is a separate run (`pytest --sim`), since a run can create only one app, and requests racing for `filelock` are tested by holding the lock while a conflicting change commits. The client tests run on Windows in the repo's `.venv`, against a `loop://` port or a fake chip reader on localhost, with a fake server. Commands are in the repo's `CLAUDE.md`.
- **Release pipeline**: builds PyInstaller client executables, Sphinx docs, and a Docker image (via VS Code's "Build/Push/Release" task), then packages a main distribution zip plus a separate vendor-JS zip (only rebuilt when JS content actually changes, tracked via a committed SHA256 manifest).

## Gotchas worth knowing

- **Windows-only clients**: internal laptop Bluetooth (CNVi/PCIe-based) can't be passed through to a Docker container via USB/IP, so `tm-reader-client` must run on Windows directly — this is a deliberate, stable design choice, not a temporary workaround.
- **Local HTTPS via Caddy**: a separate `caddy-docker` reverse proxy provides automatic HTTPS for `*.localhost` domains in dev (`https://tm.localhost` → the app's nginx container). See [infrastructure/caddy.md](../infrastructure/caddy.md).
- **JS assets are shadowed by a Docker volume mount** to an external `js-common` directory (same shared pattern as scoretility/membertility/routetility) — editing the repo's own vendor-JS files directly has no effect on the running container.
- **Bind mounts only take effect on container recreation**, not a plain restart — `docker compose down && up` is needed if a mount is missing.
- **DataTables poll returns the full dataset every tick** (not incremental) — the results view can't use DataTables server-side mode because it needs to detect row deletions across the whole finisher list; composite indexes on `Result` keep the per-race query fast enough regardless. Each poll starts only after the previous one finishes and rewrites only changed rows. Use/Ins/Del act on press, and a press on a row that has already changed is ignored with a brief notice, so a repeated Ins/Del can't shift the scan queue twice. Selecting a row holds the table still, so select the row you're working on during busy finishes ([tm-csv-connector#156](https://github.com/louking/tm-csv-connector/issues/156)).
- **Checks under `filelock` need locking reads**: MySQL's REPEATABLE READ snapshot is taken at a request's first query, before it waits for the lock. So a plain read, including a lazy relationship load, can miss a change committed during the wait. Any read under the lock that decides what to change, or what Clear All saves to its snapshot, must use `with_for_update()` ([tm-csv-connector#156](https://github.com/louking/tm-csv-connector/issues/156), [#167](https://github.com/louking/tm-csv-connector/issues/167)).
- **Trident reader connectivity is a half-open-TCP trap**: a ping reply doesn't prove the telnet session to the reader is still alive. A reader that power-cycles without sending a FIN/RST leaves a dead socket that never reports an error. `trident-reader-client` therefore enables short-interval TCP keepalive, so the OS detects a half-dead socket and the client reconnects automatically. It also debounces status changes, and the results page shows a banner and beep for degraded connectivity. After an outage of a few minutes, the reader may refuse reconnects: each one is accepted and then closed at once, likely because it still holds the old session. If the chip reader keeps reconnecting while the network is up, power-cycle the reader.
- **Bluetooth barcode scanner dropouts are silent at the serial level**: when an SPP scanner powers off, Windows keeps its virtual COM port open and pyserial reports nothing. The scanner won't reconnect to a port that's still open; only closing and reopening the port restores the link. `barcode-scanner-client` polls the Windows Bluetooth link state, and when the link drops it closes the port and keeps reopening it until the scanner is back. While the scanner is off, each open fails with a `semaphore timeout`, and a scanner that isn't in Bluetooth SPP mode fails the same way. While a scanner or chip reader client is retrying, the results page shows it as *reconnecting* (orange button reading **Stop Reconnecting**, orange banner, beep) rather than as an ordinary disconnect, and the button cancels the retries.
- **Restarting a client service**: the clients exit on NSSM's Ctrl-C within ~65ms, so `nssm restart <name>` and `Restart-Service <name>` both work ([tm-csv-connector#153](https://github.com/louking/tm-csv-connector/issues/153), [#168](https://github.com/louking/tm-csv-connector/issues/168)). A client *crash* is a different path: NSSM restarts the client by itself within ~2s, but it comes back disconnected from its device. The results page shows "client is not running" while the client is down, then a "client restarted -- click Connect" banner until the operator reconnects.
- **A Time Machine open that hangs is given up on and retried**: the Time Machine's Bluetooth serial open has hung with no error until the device was power-cycled. `tm-reader-client` gives up on an open after 15s, retries, and has the same reconnect loop, link check, and connecting/reconnecting status and banner as the scanner client. If it logs `power-cycle the Time Machine, or restart the TmReader service`, three opens are still hung and it has stopped trying. Do that, then click **Connect** ([tm-csv-connector#154](https://github.com/louking/tm-csv-connector/issues/154)).
- **A `None` race filter matches all simulation data**: results and scanned bibs belong to either a race or a simulation run, so filtering on a missing race (`race_id IS NULL`) returns every simulation-run row, not zero rows. So the results views show no rows when the session has no race or simulation run, and scan actions refuse a row that has neither ([tm-csv-connector#152](https://github.com/louking/tm-csv-connector/issues/152)). Any new query keyed on the session's race or simulation run needs the same guard.
- **Clients keep the current race only in memory**: each client starts at race 0, and the database rejects anything it posts until it's told the real race. The browser sends the race on every race change, whenever a client's WebSocket (re)connects, and in every Connect (`open`) message. A race change always reaches the server even if a client is down; that client picks up the race when it reconnects.
- **Clients send to the server one message at a time, which is what keeps scans in order**: each queues what its device sends and posts it oldest first, waiting for each answer. Keep posts serial in any client change. Server-side timestamps lag the device by up to about 0.5s in a burst. If the server is down or restarting, a client keeps the message and retries it, in order, until the server is back. If the server rejects a message, the client drops it and logs it as dropped. A lost scan shifts every later scan by one, so the clients retry rather than risk a loss, even when the post might have succeeded ([tm-csv-connector#163](https://github.com/louking/tm-csv-connector/issues/163)).
- **Recovering cleared results**: Clear All saves a per-race snapshot of results and scans before deleting, and Undo Clear restores it. The Undo button only appears right after a clear, but the restore can also be called directly for a given race. Clearing the same race again overwrites its snapshot. Clear All also checks the results view's **Ignore repeat scans** box for the race. While it's checked, a bib scanned twice in a row is recorded once ([tm-csv-connector#131](https://github.com/louking/tm-csv-connector/issues/131), [#155](https://github.com/louking/tm-csv-connector/issues/155)). Uncheck it to test the data path with the same bib, and check it again before the start.
- **Duplicate and unknown bibs are flagged, not blocked**: the results view marks a Bib No that's on more than one result, a Bib No that isn't in the race's chip-to-bib import (checked only when the race has one), and a bib scanned more than once (A, B, A, which the debounce doesn't catch; every such scan is flagged). Confirm doesn't ask about these or refuse them, so the operator checks the flagged rows before confirming. A duplicate's label gives the places of the others, and right-clicking the cell jumps to the next one. The flags are computed once per poll on the server and sent as row classes, and each row always carries a base class so that a flag clears once it's fixed ([tm-csv-connector#158](https://github.com/louking/tm-csv-connector/issues/158)).
- **Reviewing a race afterwards**: the **Results Log** view records every result and scan received, and every operator change on the results view, with a millisecond timestamp. Rows are identified by place, TM position, and bib. Use it, not the app container's log, which is lost when the container is recreated and records only database ids. A mistaken **Use** can be undone with the **Undo** button that replaces Use on that row, until the row is confirmed, its bib is edited, or Ins/Del moves a different scan onto it. The undo state is kept on the result row, not looked up in the log, because log entries identify rows by place and TM position, which change and repeat ([tm-csv-connector#161](https://github.com/louking/tm-csv-connector/issues/161)). After that, the old bib is still in the Use entry in the log. New operator actions should be logged the same way ([tm-csv-connector#157](https://github.com/louking/tm-csv-connector/issues/157)).
- **Device-read times need matching time zones**: results and scans also carry the time the client read them from the device, normally accurate to within a few tens of milliseconds, so post latency can be measured. Both times are local, so the laptop's time zone must match `TZ` in the install's `.env`. The clients themselves must not have `TZ` set, because Windows reads `TZ=America/New_York` as UTC. That's why the client debug configs load `.vscode/clients.env` instead. Don't pause reading in `data_received()`: Time Machine messages often arrive in pieces, and a pause holds each later piece until the next read cycle ([tm-csv-connector#157](https://github.com/louking/tm-csv-connector/issues/157)).

For full detail on any of the above (dev setup, full release pipeline, hardware protocols, JS architecture), see the repo's own `CLAUDE.md` linked above.
